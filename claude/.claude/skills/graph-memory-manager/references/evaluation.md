# Evaluating changes to this skill

Use this workflow when assessing a skill revision or a proposed delegation policy. Do not run it on each knowledge save. Testing reusable guidance can benefit many later sessions; reviewing every update adds recurring overhead.

Choose realistic cases relevant to the change. Useful contrasts include an empty collection gaining detailed subjects, an existing subject gaining a new detail, a brief inseparable list, and material overlapping an established branch. Judge retrieval and preservation, not exact filenames, wording, or a single preferred tree.

When delegation is available and permitted, give a fresh subagent the candidate skill, a realistic user request, and the minimum raw project artifacts in an isolated scratch workspace. It may edit only that copy and must not publish or delegate further. Do not give it the intended tree, suspected bug, proposed solution, or prior conclusions. Provide normal tool and access instructions.

Inspect the generated artifacts and actual reads, not just the agent's summary:

- Supplied facts, conditions, decision status, rationale, and required source text are preserved.
- Existing IDs and junctions are reused where appropriate; duplicate ownership and obsolete placeholders are resolved.
- Every maintained node in the affected branch has its own file in the nested parent-folder layout, with no empty leaf folders or stale duplicate files.
- Independent subjects and optional details can be retrieved separately, while short inseparable material stays together.
- Narrow reads include necessary ancestors and exclude unrelated bodies; comparisons avoid repeated ancestors.
- The project's structural and link checks pass.

If evaluating whether runtime reviewers are worthwhile, compare the candidate skill alone with the same skill plus review on equivalent fresh fixtures. Record consequential errors, correction work, total root and subagent usage where available, and elapsed time. Repeat varied cases before claiming a dependable improvement; label small samples and missing measurements. Do not infer semantic quality or cost savings from valid output schemas, character counts, or one passing run.

Keep evaluation artifacts outside maintained knowledge. Refine instructions only in response to observed failures and rerun affected cases. If an independent run is unavailable, report that limitation and distinguish local format checks from behavioral evidence. Retrieval instrumentation, when needed, is described in [audit](audit.md).

For [upgrade](upgrade.md), include an already-compatible graph after a guidance-only revision, an unversioned legacy inline graph with inbound anchors, and a graph with custom reader behavior or conflicting destinations. Check that the default command previews required changes without writing project files and waits for approval before applying them. After approval, check preservation, repaired links, explicit blockers, recoverable rollback, and no further structural changes on a second successful run. Reports and backups must stay outside reader discovery.

For [usage-report](usage-report.md), exercise on-demand narrow retrieval, unnecessary initial graph loading, justified deep traversal, and a parent-only read that misses a relevant child's constraint and causes an incorrect answer or rework. Check that the report explains the sequence and visible triggers, names avoidable reads or missed knowledge, and connects them to task correctness. Include justified rereads after compaction or source changes, a task change that invalidates initial audit targets, and an internal full-file scan that emits only selected bodies; none alone establishes waste.

Also cover missing instrumentation, incomplete history, and an unrelated retained audit run. Compare a stated full-graph-once baseline with cumulative selective reads, including discovery and repeated ancestors; lower unique coverage alone must not imply token savings. Verify that missing required facts prevents a successful-efficiency verdict, retrospective checks are excluded from original retrieval totals, unsupported metrics stay unknown, and the handoff contains portable evidence and bounded maintenance proposals. These scenarios test report behavior; structural validators alone do not establish that they passed.
